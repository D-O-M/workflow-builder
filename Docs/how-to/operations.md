# Diagnose a Process that appears stuck

Record the environment, UTC time window, Blueprint version, Process ID and runtime Step ID before following a case below. An iterated Blueprint node can have several runtime Step IDs. Open the existing Process in Process Explorer. Use that same ID to verify recovery, since starting another Process can repeat business work. The [deployment views](../architecture/deployment.md) identify which workers and telemetry are available in each environment.

## 1. A Step stays Pending

1. Read the Process detail from `GET /api/processes/{processId}`. In Cosmos, inspect the corresponding `processsteps` record and its dispatch state. Look for a durable intent in `processstepdispatches`. For a Process with no initial Step, inspect its `start` snapshot instead.
2. If a dispatch intent is pending, check its next attempt time and last error. Look at Dispatcher logs, `process_step_dispatch_pending` and `process_step_dispatch_oldest_pending_age_ms` where metrics are collected. The API or Engine attempts immediate delivery first. Dispatcher drains outstanding intents. In the Azure demo check its replica count as well as the Service Bus queue depth.
3. If the intent is dispatched, check the Engine's connection to the `processsteps` queue, active and dead-letter message counts, and Engine logs for the Step ID. Restore the affected worker, connection or Plugin prerequisite indicated there. For a missing initial Step, Maintenance can repair eligible pending Processes from their saved start snapshot when its `ProcessStartReconciliation:Enabled` setting is true.
4. **Verify** that the original Step advances to `InProgress` or a terminal state and the next expected Step appears. Read the source record if the graph still shows Pending. [Dispatch service](../../Backend.Services/ProcessStepQueue/ProcessStepDispatchService.cs) · [Start reconciliation](../../Backend.Maintenance/ProcessStartReconciliationService.cs)

## 2. A Plugin result arrived but the Step did not finish

1. Find the Step's `processstepfinalizations` document by runtime Step ID. Inspect its outcome, last checkpoint and error alongside the Engine logs for that Step. A saved `ResultReceived` means the Engine received the result. Later checkpoints distinguish persisting outputs or failure, downstream activation, and updating the Process. [Engine execution and checkpoint sequence](../architecture/engine-execution.md)
2. If the Engine lost its Service Bus lock or stopped, restore the affected dependency and let the Engine receive the message again. It resumes from the durable checkpoint. Reinvoking the Plugin directly can duplicate its external effects.
3. For an older incomplete record, inspect the Maintenance process and its logs. Both the process and its `FinalizationRecovery:Enabled` setting must be active for recovery outside a queue delivery. Local Development starts Maintenance by default with recovery disabled. The Azure demo default omits the worker. Its default minimum record age is five minutes. Preserve the failure details and escalate a record marked unrecoverable or at the retry limit to the Engine maintainer.
4. **Verify** that the checkpoint advances to `QueueMessageCompletionPrepared` on the Engine path or `RecoveredWithoutQueueMessage` on the Maintenance path. Check the original Process and its expected downstream Steps. The recovery counter `process_step_finalization_recovered_total` records successful Maintenance recoveries. [Stage machine](../../Backend.Engine/ProcessStepFinalizationStageMachine.cs) · [Recovery worker](../../Backend.Maintenance/StepFinalizationRecoveryWorker.cs) · [Recovery options](../../Backend.Maintenance/StepFinalizationRecoveryOptions.cs)

## 3. A Plugin is missing from the catalog or unavailable to the Engine

1. Identify the Plugin name, version and target Engine runtime. For a fresh local checkout, check the matching ZIP exists under `Backend.Plugins/_bundles`, then check the `plugins` blob container. PluginSeeder logs when the local bundle directory is missing. [Build canonical bundles](../agent-context/developer-workflows.md#rebuild-canonical-plugin-bundles)
2. Inspect `GET /api/admin/plugin-ingestions?pluginName={name}` for the recorded ingestion status and error. If the blob exists with no record, check PluginDetector's trigger and reconciliation logs, storage binding and SQL connection. Fix the reported package or deployment problem before retrying through the normal upload path.
3. If registered, inspect the specific task version in `GET /Tasks`. The catalog includes Engine runtime availability. For a missing capability or configuration, correct the declared requirement on the target Engine. For ABI errors, rebuild and ingest a compatible bundle. For an Engine quarantine, use its Plugin-agent health logs to establish what failed. The ingestion quarantine and the Engine's runtime quarantine have separate owners.
4. **Verify** the intended task version reports `Runnable` on an available Engine and a known-safe test Blueprint using it completes. [Catalog status selection](../../Backend.API/Services/TaskCatalogQueryService.cs) · [Plugin development](../agent-context/plugin-development.md)

## 4. Dashboard figures, Process Explorer progress or logs are stale

| Symptom | Evidence and action |
| --- | --- |
| Dashboard totals or recent Processes look old | Dashboard fetches HTTP summaries on load and when the selected Blueprint or time window changes. Repeat the same query in the same window and inspect `/api/observability/processes/summary` and `/api/observability/processes/recent`. Compare with canonical Process and Step state. When asynchronous projections are configured, check ProjectionWorker's `processprojectionleases`, `projection_worker_lag_ms` and failure logs. |
| Process Explorer changes only after refresh | Keep the affected Process selected during a new Step transition. Check canonical `processsteps`, realtime projections, the broadcaster's change-feed startup and read/publish calls to SignalR. In the browser, check `/runtime-bootstrap.json`, the API's `/api/client-config`, connection to `/hubs/processes`, and subscriptions. If publisher requests are rejected, inspect the configured publisher credentials. The broadcaster sends batches for active subscriptions. |
| Process status is correct but log lines are missing | The log pane reads the API's Loki-backed log endpoints and streams via server-sent events. Check the UTC time window, the browser's HTTP status, the API's Loki URL, and Alloy's log export. In local Grafana, query `{service_name=~".+"} | process_id="<Process ID>"`. AppHost with observability disabled and the unmodified Azure demo lack this log backend. For the demo use the service's available runtime logs to investigate. |

**Verify** the affected path independently. Re-fetch Dashboard for the chosen window, observe `processSummaryUpdated` or `processStepsUpdated` on the subscribed Process Explorer during a real state change, or find a newly emitted log entry with the same Process ID in both Loki and the pane.

# What the seven stakeholder reviews changed

One dedicated agent reviewed the code from each [documented role](../../stakeholder-roles/README.md). The agents traced different paths and challenged the order of work. Their judgments are proposed acceptance criteria. Actual deployment exposure, customer impact and investment priorities still need confirmation from the people responsible.

| Role | Judgment that affected the audit | What that role would ask to see |
| --- | --- | --- |
| [UP-01 Business process owner](../../stakeholder-roles/business-process-owner.md) | Recovery comes first, but complete search belongs in the same release when staff use it to account for affected customers. An accepted child ID and an apparently complete list both make business promises. **R3, R4, R6** | Interrupt and repeat one phase trigger. Retrieve exactly one child, then find its older failed account on a later search page even after a newer iterator item succeeds. |
| [UP-02 Blueprint author and maintainer](../../stakeholder-roles/blueprint-author-and-maintainer.md) | Fix the Phase Series round-trip and historical Plugin provenance before moving editor components. An author should be able to explain which design was tested and which implementation ran. **A1, A2, R2, P4** | Edit only a Data Bridge in a mixed Latest/Pinned series. Publish another Blueprint and verify only Latest follows it. Register a new Plugin patch and inspect the previously completed Step’s actual version. |
| [UP-03 Process operations team](../../stakeholder-roles/process-operations-team.md) | Operators can tolerate a delayed display only if the runbook gives them a reliable way to check the original outcome and identify uncertainty before replay. Otherwise the display issue also becomes a recovery gate. **R1, R5, R8, R9** | Withhold the last realtime event after one external effect. Use the original Process/Step IDs to reconcile it, recover where safe and verify one external effect and eventual agreement in Explorer. |
| [UP-04 Platform and cloud team](../../stakeholder-roles/platform-and-cloud-team.md) | An empty-queue Dispatcher and an orphaned Engine claim need independent recovery checks. Keeping a Dispatcher warm addresses only the former. Gate workloads using real credentials on effective identity isolation. **P7, R1, P8** | Start with idle workers, fail the first queue send and restore the broker without adding traffic. Stop the Engine during execution. Follow the same Process to completion or a durable uncertain outcome, with an external-effect ledger. |
| [UP-05 Core engine developer](../../stakeholder-roles/core-engine-developer.md) | Step-local version selection can ship independently. Claim recovery must account for older Engines that still acknowledge an in-progress redelivery. Extract the queue-free finalizer after its behavior is characterized. **R2, R1, E3** | Replay an older checkpoint using its recorded version. Exercise an ownerless legacy claim and a late result after takeover. Confirm safe settlement across a mixed-version rollout or require older consumers to drain. |
| [UP-06 Plugin developer](../../stakeholder-roles/plugin-developer.md) | Protect the credential destination before enabling a keyed Plugin for additional callers. Enforce immutable release bytes before the next Plugin release. Admin authorization alone cannot constrain input to an already permitted task. **P1, P2, P3, P4, P5** | An existing Blueprint uses its configured endpoint successfully. An unapproved origin receives neither credential nor XML. Two independent publishers can repeat identical content, while different bytes require a new version. |
| [UP-07 Platform product owner](../../stakeholder-roles/platform-product-owner.md) | Demonstrate recovery from accepted request through Explorer before widening adoption. Measure the work of a second team trying an existing task. Runtime availability queries and vocabulary should make that journey easier to understand. **R1, R3–R5, A5, A6** | A second team imports, configures, runs and diagnoses a task without edits from its creators. Record where they need help and how long diagnosis takes. Discovery provides no measured adoption baseline or market validation. |

## Decisions for the owners

- **Uncertain external effects.** Agree which tasks can safely retry, which can query the external system by idempotency key, and which require an operator. Engine recovery and operator tooling both depend on this answer.
- **Visibility during incidents.** Agree the maximum acceptable age of projections and how to expose partial Dashboard counts. Test these as service promises with operators.
- **Version and access policy.** The direct start route selects the latest Blueprint version, while a Phase Series supports an explicit version policy. Decide whether external callers also need a pinned direct start. Agree who can mutate Plugin ingestion state, author Blueprints and start Processes. The audit records the current boundaries and a demonstrated editor round-trip defect. [Process API](../../how-to/process-api.md) · [Access model](../../authentication-keycloak.md)
- **Evidence of adoption.** Faster catalog access and clear error messages are measurable code changes. The value to a second team needs observation with that team. [Discovery notes](../../product/discovery-notes.md)

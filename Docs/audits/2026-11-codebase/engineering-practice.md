# Naming, structure and development practice

## E1 · Medium · The same ID name means two different things in one operation

The accepted start result uses `BlueprintId` for the **definition** a caller started. The persisted Process field named `BlueprintId` receives the **version**. The same start method logs an `initialProcessStepId` under `InitialBlueprintNodeId`. Searching telemetry by the displayed field, or joining state to the catalog by the apparent ID, can lead a maintainer to the wrong object. These are four distinct identities with different lifetimes. [Acceptance result](../../../Backend.API/Services/BlueprintProcessService.cs#L15-L20) · [Step identity and stored version](../../../Backend.API/Services/BlueprintProcessService.cs#L92-L132) · [Log fields](../../../Backend.API/Services/BlueprintProcessService.cs#L160-L163) · [Returned ID](../../../Backend.API/Services/BlueprintProcessService.cs#L199-L202)

**Change and verify.** Use `BlueprintDefinitionId`, `BlueprintVersionId`, `BlueprintNodeId` and `ProcessStepId` at internal boundaries. Preserve existing JSON names and Cosmos partition keys through explicit mapping. Emit the two Step/node log fields separately and migrate dashboard queries that consume them. Test with deliberately different definition/version IDs and node/Step IDs. Keep compatibility fixtures for existing clients and stored documents.

## E2 · Medium · Two start methods implement the same durability protocol

`StartLatestVersionAsync` and `StartVersionAsync` each materialize inputs, write Process state, create a Step, dispatch it and update projections. Their differences matter, especially the reserved child ID and phase metadata. A change to persistence ordering or telemetry currently needs review in both bodies. This is precisely the protocol that must stay consistent across retries. [Definition-based start](../../../Backend.API/Services/BlueprintProcessService.cs#L54-L202) · [Version-based start](../../../Backend.API/Services/BlueprintProcessService.cs#L205-L351)

**Change and verify.** Keep version lookup and ownership validation at each entry point. Share the operation that starts an already resolved version, with its Process ID, phase metadata, hydration plan and timestamps explicit. Exercise ordinary and phased starts at each write failure, comparing accepted IDs, initial inputs, dispatched work and recovery.

## E3 · Medium · A queue-free recovery operation requires a fabricated broker message

Maintenance references the Engine executable project. To call the shared finalization path it constructs an implementation of the queue-message interface with synthetic timestamps and settlement methods that throw. An apparently valid interface call in a future refactor could break only the recovery path. The Engine’s named stages and recovery tests give this refactor a natural boundary. [Project dependency](../../../Backend.Maintenance/Backend.Maintenance.csproj#L19-L25) · [Recovery entry](../../../Backend.Maintenance/StepFinalizationRecoveryService.cs#L189-L205) · [Synthetic message](../../../Backend.Maintenance/StepFinalizationRecoveryService.cs#L289-L314) · [Finalization entry points](../../../Backend.Engine/StepFinalizationService.cs#L213-L249)

**Change and verify.** Model durable finalization inputs independently of broker ownership. Let the Engine adapter own settlement, and let Maintenance resume using the stored checkpoint. Replay old checkpoint shapes and simulate failure at each stage with and without a broker message before extracting a shared library.

## E4 · Medium · Assembly, folder and namespace names obscure contract ownership

`Backend.DTOs/Backend.Models.csproj` contains input/view models, an executable Blueprint and entity-aware mappers. It references the relational project. An interface in `Backend.Interfaces` consequently returns an EF entity from one method and API-facing view models from others. Separately, persisted records are in `Backend.ProcessState.Contracts` under the namespace `Backend.Database.State.Objects`, while the Cosmos project is named `Backend.State.DAL/Backend.Database.State.csproj`. Following a type name alone sends a new maintainer to the wrong assembly. In the audited conditional-branch edits, the backend model project also embeds the operator catalog directly from the Angular domain folder. A frontend directory move can break backend compilation. [Model project](../../../Backend.DTOs/Backend.Models.csproj) · [Mixed repository contract](../../../Backend.Interfaces/Repositories/IPhasedBlueprintRepository.cs#L1-L21) · [State contracts](../../../Backend.ProcessState.Contracts/ProcessStateRecords.cs) · [Cosmos project](../../../Backend.State.DAL/Backend.Database.State.csproj)

**Change and verify.** Split source files first by the concept they own, such as dispatch, finalization, projection and Plugin ingestion. Retain public types and serialization names during that move. At the next feature boundary, make it explicit which layer translates entities into application reads and API views. Give shared operator data a neutral contract location, with one producer and two tested consumers. Compile both consumers, deserialize a pre-change record and compare API payloads before considering assembly renames.

## E6 · Medium · Public-looking examples and unfinished contracts misdirect contributors

`ITaskDefinitionRepository.CreateTaskSchema` advertises a usable operation. Its implementation contains a commented-out old schema path and always throws `NotImplementedException`. The task controller contains a second ten-item sample catalog even though GET uses the query service. Both the API and the Engine still contain template weather controllers. An API authentication test actually calls the weather route, so removing scaffolding requires moving that test to a representative route. The field `_nanoServiceOrchestrator` in the reload consumer also sends readers searching for an older concept when the type is `PluginRuntimeOrchestrator`. [Repository contract](../../../Backend.Interfaces/Repositories/ITaskDefinitionRepository.cs) · [Unimplemented method](../../../Backend.Repositories/TaskDefinitionRepository.cs#L164-L211) · [Catalog controller](../../../Backend.API/Controllers/TasksController.cs#L18-L34) · [Weather test](../../../Backend.API.Tests/AuthenticationEndpointTests.cs#L25-L36) · [Reload consumer](../../../Backend.Engine/PluginReloadConsumer.cs#L7-L18)

**Change and verify.** Verify external use of published contracts, retire obsolete internal operations, and delete the sample catalog after a usage search. Make authorization coverage exercise a real protected route. Rename the private field to match its responsibility. Verify the OpenAPI surface and the catalog registration test after cleanup. Reserve `WorkflowBuilder` for product identifiers and preserve existing public wire names when tidying internal terminology.

## E7 · High for change confidence · Repository CI omits fast tests and misaligns screenshot baselines

The checked-in pull-request workflows run documentation checks and UI-path-filtered mocked Playwright. The integration workflow is manually dispatched. There is no checked-in PR job running the backend unit suites or the documented Vitest lane. The mocked browser job runs on Ubuntu, but the four tracked expected screenshots are suffixed `chromium-win32.png`. The project uses default platform-qualified screenshot paths. A clean Linux runner lacks the corresponding Linux expectations. External branch protection or CI was outside this review. [PR browser job](../../../.github/workflows/ui-playwright.yml#L3-L34) · [Manual integration lane](../../../.github/workflows/integration-tests.yml#L1-L26) · [Browser configuration](../../../UI/playwright.config.ts) · [Example baseline](../../../UI/e2e/specs/dashboard.spec.ts-snapshots/dashboard-loaded-chromium-win32.png) · [Unit and build scripts](../../../UI/package.json)

**Change and verify.** Gate affected changes with a .NET build and fast non-distributed tests, Vitest and the Angular production build. Use a consistent reference platform for screenshot generation and verification. Retain the separate distributed lane. Submit intentional backend and frontend unit failures in a trial branch and confirm the relevant check blocks each. Review image differences rather than automatically approving refreshed baselines.

## E8 · Medium · The integration runner’s cleanup scope exceeds its own test session

Before a test, the runner stops the repository AppHost, enumerates processes globally by name and force-stops matches, then shuts down .NET build servers. Even a `-NoBuild` run performs this cleanup. On a shared developer machine or a parallel checkout, an integration test can interrupt another session. The docs warn developers to separate smoke and integration sessions, but both still share host resources. [Runner cleanup](../../../IntegrationTests/scripts/run-integration-tests.ps1#L17-L58) · [Development workflow](../../agent-context/developer-workflows.md#integration-and-smoke-entry-points)

**Change and verify.** Record the resources and PIDs created by an individual invocation and clean those up in its teardown. Make wider stale-resource recovery an explicit operation. Run two isolated sessions and stop one. Verify the other keeps its worker, AppHost and build session.

## E9 · Medium · Several generated contracts still have manually synchronized consumers

The topology emitter and tests check the exported JSON against the C# topology. Terraform separately declares the Cosmos container names and partition paths. Plugin projects, integration fixtures and performance fixtures also carry near-identical contract generation targets. Each invokes the emitter and copies generated metadata to the project directory after a normal build. A packaging change can reach one family of Plugins while fixture builds still exercise older rules, and validation builds can rewrite tracked source artifacts. [Topology parity test](../../../Backend.Topology.Tests/WorkflowBuilderTopologyValidatorTests.cs#L50-L66) · [Terraform catalog](../../../Infra/Terraform/locals.tf#L11-L27) · [Product targets](../../../Backend.Plugins/Directory.Build.targets) · [Integration targets](../../../IntegrationTests/Plugins/Directory.Build.targets) · [Performance targets](../../../PerformanceTests/Plugins/Directory.Build.targets)

**Change and verify.** Consume the generated topology in Terraform or compare the planned container/key pairs against it. Share the contract generation target, parameterizing paths that genuinely differ. Separate generation under `obj` from the deliberate refresh of checked-in examples. Build a representative product, integration and performance Plugin in a clean tree. Compare manifest/ABI/schema outputs, and check that a second ordinary build leaves sources untouched.

## E10 · Medium · Restore warnings repeat across projects without informing a release decision

On the isolated solution build NuGet reported 372 warnings across the project graph, including NU1902 and NU1903 for `System.Security.Cryptography.Pkcs` and `System.Security.Cryptography.Xml`. These are repeated package advisory reports. The count measures build noise, and says nothing about how many application paths are exploitable. Central package management already gives maintainers one place to control the directly pinned XML package. [Central versions](../../../Directory.Packages.props)

**Change and verify.** Produce a deduplicated inventory of affected versions and dependency paths, identify runtime use versus tooling, then update or document a time-bounded decision for each advisory. Make new unresolved high-severity advisories visible in the PR lane. Rebuild cleanly, re-check the dependency graph and run the consuming Plugin/security tests. Advisory exploitability and remediation versions require a separate dependency review.

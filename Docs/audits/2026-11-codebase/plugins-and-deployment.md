# Plugin contracts, access and deployment

[Audit overview and priorities](README.md) · [Process execution and recovery](runtime-and-data.md)

## P1 · High · A caller-selected DCC destination receives the configured gateway credential

`GatewaySubmitPlugin` prefers `Input.EndpointUrl` over the configured endpoint. It sends the XML and attaches the deployment’s bearer credential to the selected URI. Capability validation checks the configured endpoint. A caller who can supply this Plugin input can select a different reachable destination when a gateway key is present. [Endpoint selection](../../../Backend.Plugins/Dcc.GatewaySubmit/GatewaySubmitPlugin.cs#L183-L190) · [HTTP request](../../../Backend.Plugins/Dcc.GatewaySubmit/GatewaySubmitPlugin.cs#L109-L123) · [Capability definition](../../../Backend.Engine.Capabilities/BuiltInCapabilities.cs#L65)

**Reproduced.** A temporary .NET 10 probe ran the Plugin with in-memory XML, synthetic credentials and a capturing HTTP handler. Both the configured origin and a different input-supplied origin received the same bearer and full XML. All requests terminated in that handler.

**Change and verify.** Make destinations and credentials a deployment-owned pair. If authors need alternatives, let them choose among named approved endpoints. Validate the final URI before releasing either the credential or XML. Preserve the configured-endpoint case and require zero captured requests for an unapproved origin. Check redirects under the same policy.

## P2 · High · A checkout cleanup path can escape its workspace

`SafeBuildId` permits dots, including the entire value `..`. Checkout builds a path from the work root, this ID and `repo`. With cleanup enabled, it deletes that directory recursively before cloning. The input also accepts a work root. Where callers can influence these values and the Engine account can write the parent directory, cleanup can target a sibling checkout. The name `SafeBuildId` promises more than its character substitution enforces. [Path handling](../../../Backend.Plugins/CiCd.Common/CiCdPaths.cs#L20-L25) · [ID normalization](../../../Backend.Plugins/CiCd.Common/CiCdPaths.cs#L45-L54) · [Allowed characters](../../../Backend.Plugins/CiCd.Common/CiCdPaths.cs#L78-L79) · [Cleanup](../../../Backend.Plugins/CiCd.GitCheckout/GitCheckoutPlugin.cs#L13-L25)

**Change and verify.** Keep the allowed base in deployment configuration. Reject navigation segments and reserved names, and verify the canonical deletion target is a descendant of that base under host path rules, including links. Use a disposable sandbox with a sibling sentinel. Check ordinary IDs, `..`, an alternate root and a link escaping the test workspace before exercising cleanup.

## P3 · High for a shared deployment · An “admin” route has the ordinary authenticated-user policy

The API installs a global authenticated-user filter. The Plugin ingestion controller exposes quarantine and unquarantine with that filter alone. A signed-in caller with an otherwise read-only role can therefore request a durable change to a bundle’s ingestion status. The repository documents this boundary, but the route name and defined `Admin` policy suggest a stronger guarantee to someone extending it. Direct controller tests exercise the status store without passing through authorization. [API filter](../../../Backend.API/Program.cs#L124-L127) · [Admin actions](../../../Backend.API/Controllers/PluginIngestionAdminController.cs#L50-L68) · [Controller tests](../../../Backend.API.Tests/PluginIngestionAdminControllerTests.cs#L73-L95) · [Current access model](../../authentication-keycloak.md#api-and-signalr)

**Change and verify.** Agree who may read ingestion diagnostics and who may mutate them. Put the mutation policy on the actual HTTP endpoint. Test unauthenticated, authenticated read-only, authorized administrator and service-account requests through the middleware, with a store spy proving denial produces no write. Carry the same review to Blueprint authoring and Process start before promising separation between teams.

## P4 · High · Publishing can replace the executable behind an existing Plugin version

Version selection relies on a previous bundle in the local output directory. A clean checkout starts with the declared project version. The Azure job builds before downloading any release history and uploads with overwrite enabled. A changed implementation with the same declared version can replace the blob while ingestion finds the existing name/version in SQL. Two Engines can then execute different bytes under the same reported identity. This affects both incident reconstruction and the meaning of a versioned Blueprint. [Version selection](../../../BuildScripts/bundle-plugins.ps1#L518-L551) · [Deployment build](../../../.github/workflows/deploy-azure-demo.yml#L761-L778) · [Blob publication](../../../.github/workflows/deploy-azure-demo.yml#L799-L806) · [Existing catalog entry](../../../Backend.Repositories/TaskDefinitionRepository.cs#L105-L117) · [Engine load](../../../Backend.Engine/PluginRuntimeOrchestrator.cs#L607-L638)

**Change and verify.** Publish an immutable release identity with a canonical payload digest. Make identical repeats idempotent and atomically reject a different payload for an existing identity. Build from two clean checkouts, change implementation without changing the declared version, and race two publishers. Require an actionable conflict, continued access to the original bytes, and agreement between catalog and Engine. Include a deliberate new patch and a rolling restart.

## P5 · High when scaled out · A reload sent to one queue does not refresh every Engine

Registration emits a reload message to one shared queue. The receiving Engine updates its local runtime and completes the message. Other replicas can keep serving a previously available patch because a successful local resolution bypasses reload. A registration followed by a failed notification also needs reconciliation. [Registration and send](../../../Backend.Services/PluginBundleProcessingService.cs#L208-L225) · [Receiver wiring](../../../Backend.Engine/Program.cs#L219-L223) · [Local reload and completion](../../../Backend.Engine/PluginReloadConsumer.cs#L32-L43) · [Resolution fast path](../../../Backend.Engine/StepExecutionService.cs#L414-L430)

A later working-tree edit adds management-mode reconciliation. Policy changes, retries and a capability deadline can prompt refreshes there. The management-disabled mode waits after its initial load, and neither mode compares a per-replica catalog revision. [Reconciliation conditions](../../../Backend.Engine/PluginRuntimeOrchestrator.cs#L80-L121)

**Change and verify.** Give each Engine a durable catalog revision it can compare with its loaded revision. Notifications can shorten that interval. Publish a new eligible patch with two warm replicas, drop the first notification and verify both converge within the agreed time without restarting. Keep already claimed Steps on their recorded version.

## P6 · Medium · The generator treats unrelated builder calls as Plugin declarations

The Roslyn generator gathers member invocations named `Build` before establishing their symbol identity. Chain parsing can report a Plugin diagnostic for ordinary builder calls. A developer can break Plugin compilation by adding a second library’s `reportBuilder.Build()` in the same assembly. The contract parser, schema builder and generated-code emitter also share one 2,128-line source file, which raises the cost of finding where that diagnostic originated. [Candidate collection](../../../Backend.Plugins.Harness.Generator/PluginContractGenerator.cs#L97-L117) · [Chain diagnostic](../../../Backend.Plugins.Harness.Generator/PluginContractGenerator.cs#L170-L179)

**Change and verify.** Filter on the resolved harness builder method before diagnosing its chain. Separate candidate recognition, contract validation and output emission behind the existing generated contract. Compile one fixture containing both builders and a second with a genuinely invalid Plugin chain. Assert the diagnostic ID, source location and generated manifest for each relevant case.

## P7 · High for scale-to-zero · The Dispatcher wakes on its output

The Dispatcher polls durable intents in Cosmos, but the demo allows zero replicas and its scale rule watches the output Service Bus queue. When an immediate send fails on an otherwise idle system, a due intent can exist with an empty queue and no Dispatcher to retry it. Projection and Maintenance are also polling workers. Enabling one with zero minimum replicas needs an independent wake source. Enabling asynchronous projection also changes the Engine’s write behavior. [Dispatch retry loop](../../../Backend.Dispatcher/ProcessStepDispatchWorker.cs#L25-L32) · [Intent processing](../../../Backend.Services/ProcessStepQueue/ProcessStepDispatchService.cs#L345-L397) · [Demo setting](../../../Infra/Terraform/environments/demo/terraform.tfvars.example#L44-L48) · [Worker scale configuration](../../../Infra/Terraform/main.tf#L333-L397) · [Projection mode](../../../Infra/Terraform/locals.tf#L127-L130)

**Change and verify.** Keep a poller warm or wake it from its durable input. Make unsupported zero-replica combinations fail configuration validation. Start with empty queues, fail the first send, restore connectivity and introduce no new traffic. The originally accepted Process should finish. Repeat with a pending projection and a finalization checkpoint for their respective workers.

## P8 · High for credential isolation · Separate identities can read the same privileged secrets

The Terraform configuration for the shared platform vault assigns each service identity App Configuration read access and the vault-wide Secrets User role. The shared environment configuration includes privileged SQL, Cosmos, Storage, Service Bus and publisher credentials. Separating managed identity names does little to contain a compromised workload if the SignalR identity can resolve the migration SQL credential. [Role assignment scopes](../../../Infra/Terraform/main.tf#L160-L189) · [Shared secret references](../../../Infra/Terraform/locals.tf#L217-L227) · [Configuration selection](../../../Backend.ServiceDefaults/Extensions.cs#L131-L145)

**Change and verify.** Enumerate the data-plane permissions per workload. Separate migration credentials from runtime access, narrow configuration selection and enforce the separation at the vault or resource. Test under the actual service principals in a disposable deployment. SignalR should serve authorized subscriptions while being denied retrieval of the database administrator credential.

## P9 · Medium · The ZIP extraction check accepts a sibling with the same path prefix

The extractor normalizes an entry path, then checks whether its text starts with the destination path using a case-insensitive comparison. A destination named `stage` also matches `stage-adjacent`. Detector/seeder ingestion and Engine loading pass the factory’s workspace through the blob source to this extractor. The production factory includes a fresh GUID in the directory name. Exploiting this particular sibling-prefix case via remote upload would require knowledge of that name. [Containment check and write](../../../Backend.Utilities/PluginArchiveExtractionUtility.cs#L40-L66) · [Workspace factory](../../../Backend.Utilities/PluginWorkspaceFactoryUtility.cs#L17-L31) · [Bundle source](../../../Backend.Services/PluginBundles/BlobPluginBundleSource.cs#L30-L37)

**Reproduced.** The compiled extractor processed an in-memory archive inside a disposable sandbox. It wrote the intended marker under `stage`, also wrote a marker under `stage-adjacent`, and skipped a different sibling named `other`. The test supplied the target directory directly.

**Change and verify.** Use a path-component boundary with filesystem-appropriate casing or a standard extractor with equivalent guarantees. Reject traversal before partially extracting a release. Test a valid entry, a prefixed sibling, a different sibling and case variants on the supported hosts.

## Supplement · Engine Management changes that arrived during the audit

These two observations are from a later static read of the uncommitted Engine Management feature. They sit outside the snapshot build and test totals. Its controller requires the runtime engineer policy, rejects the auth-disabled fallback and separately gates writes. Its dedicated Plugin secret vault grants distinct write and read roles to the API and Engine. Preserve those decisions when addressing P3 and P8. [Controller guards](../../../Backend.API/Controllers/EngineManagementController.cs) · [Dedicated vault](../../../Infra/Terraform/engine-management.tf#L8-L50)

- **M1 · Medium · A rejected secret edit can leave a credential version behind.** The API checks the policy revision, creates a secret version, then attempts a separately guarded SQL change. A competing edit or SQL failure can leave a stored secret with no winning policy reference. The effective policy retains its winning value. Track credential creation with an idempotent write intent or reconcile orphaned versions under a separate, narrowly privileged identity. Race two writes with the same revision and interrupt after secret creation. Account for each stored version without removing the winning credential. [Endpoint ordering](../../../Backend.API/Controllers/EngineManagementController.cs#L100-L116) · [Revision guard](../../../Backend.Services/EngineManagement/EngineManagementStore.cs#L78-L96) · [Version creation](../../../Backend.Services/EngineManagement/ManagementSecretStore.cs)
- **M2 · Medium · The management screen can keep showing the old serving Plugin.** The API combines current runtime availability with serving-version IDs. The UI polls fleet status but reloads Plugin rows on selected changes to the aggregate status or policy revision. A patch failover can change the serving version while both values stay constant. Include an observed-state revision or refresh the visible Plugin query periodically. Test a failover at the same policy revision and fleet label without manually reloading the page. [Status assembly](../../../Backend.API/Controllers/EngineManagementController.cs#L50-L70) · [Client polling](../../../UI/projects/engine-management/src/management-page.ts#L54-L78)
